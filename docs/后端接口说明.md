# 学校后端接入与数据要求

本文说明当前客户端调用的学校管理系统接口，以及上线前后端需要确认或提供的数据。所有服务地址和微信参数由部署人员写入安装机器的 `config.json`；不得把生产域名、账号、令牌、密钥或证书放进源码、示例配置或 Git。

## 部署配置

首次启动会在 Electron 用户数据目录生成 `config.json`。教师端和学生端使用各自的数据目录。按部署环境填写：

```json
{
  "role": "teacher",
  "stationId": "CLASSROOM-PC-01",
  "teacherUrl": "http://127.0.0.1:41731",
  "listenHost": "127.0.0.1",
  "listenPort": 41731,
  "schoolName": "学校名称",
  "schoolLogoPath": "C:/School/config/logo.png",
  "schoolServerUrl": "",
  "wechatAppId": "",
  "wechatRedirectUri": "",
  "tls": {
    "certPath": "C:/School/certs/teacher.crt",
    "keyPath": "C:/School/certs/teacher.key"
  }
}
```

`schoolLogoPath` 可省略；支持 PNG、JPEG、WebP、GIF，最大 2 MiB。学校服务和微信字段未填写时，应用仍可启动，但学校登录、班级同步不可用。学生端的 `teacherUrl` 应指向教师端 HTTPS 地址；HTTP 仅允许回环地址供本机调试。私钥和证书文件应由部署系统提供，并保存在 Git 仓库之外。

`wechatAppId` 是应用标识，不等于密钥。若微信服务商要求 AppSecret，应由学校后端保管，桌面客户端不得持有或请求该密钥。

学校提供品牌图时，可用 `python tools/make-icon.py <学校Logo图片路径>` 生成安装程序和托盘图标。生成文件仅留在本地，不提交 Git；渲染界面 Logo 通过 `schoolLogoPath` 独立配置。公开仓库不包含任何学校 Logo。

## 当前客户端依赖的学校接口

所有学校 API 使用 `schoolServerUrl` 作为基址，接受 JSON。除微信回调外，已登录请求携带 `Authorization: Bearer <token>`。通用业务响应格式为：

```json
{"code":200,"msg":"ok","data":{}}
```

| 方法与路径 | 用途 | 客户端依赖的数据 |
| --- | --- | --- |
| `GET /wechat/callback?code=...&state=...` | 用微信授权码登录/绑定账号 | `data.token`、`data.refreshToken`、`data.userId` |
| `POST /user/refresh` | 刷新登录凭据 | 请求 `{ "refreshToken": "..." }`；返回新的 `token`、`refreshToken`、`userId` |
| `DELETE /user/logout` | 服务端注销当前 token | 标准成功响应 |
| `GET /user/info` | 获取当前教职工资料 | `id`、`userName`、`empName`、`avatar`、`phoneNumber`、`empId`、`roleList`（角色项含 `name` 或 `alias`） |
| `GET /classes?isGraduated=0` | 查询未毕业班级 | 数组或 `{ "records": [...] }`；班级项含 `id`、`className`，可选 `departmentName`、`advisorName`、`size` |
| `GET /student?classId={id}&page={n}&limit=200` | 按班级分页读取名册 | `data.records`、`data.pages`；学生项含 `id`、`name`、完整 `idCard`，可选 `gender` |

客户端按 `code === 200` 判断业务成功，401 会触发一次刷新并重试。错误响应应提供可向管理员展示的 `msg`。班级列表兼容 `data` 直接为数组或 `data.records`。学生列表使用 `records` 与 `pages` 翻页，页码从 1 开始；也可提供 `total`，但当前客户端不以它作为结束条件。

### 身份与隐私要求

- 学生名册必须仅返回所请求 `classId` 的学生，并按已授权教师身份做服务端权限检查。
- 为完成本地名册核对，客户端当前需要完整的 18 位身份证号。脱敏号码会被拒绝；若学校政策不允许向终端提供完整号码，应由后端提供专用的服务端签到核验接口，客户端改为提交授权凭据与核验结果，不能通过降低客户端检查来绕过。
- `id` 应稳定且在学校范围唯一；`idCard` 在班级内应对应唯一学生。重复记录会按学生 `id` 合并并计入名册提示。
- `avatar` 可为 HTTP(S) 图片 URL 或 data URL。客户端只加载 PNG、JPEG、WebP、GIF，限制 2 MiB；同源请求可携带当前 token。
- 登录 token 和 refresh token 不应记入服务日志。客户端尽可能使用操作系统安全存储保存 refresh token；注销或刷新失败时删除本地凭据。
- 当前教师端的 `teacher-state.json` 会在 Electron 用户数据目录保存场次、签到记录和完整学生名册（包括身份证号），文件本身未加密。部署时应使用受控的 Windows 用户账户和磁盘权限，并制定清理期限；正式部署前建议改为不持久化原始身份证号，或加密存储。

## 签到业务数据

学生端不直接连接学校 API，而是向教师端提交签到请求。教师端目前本地校验名册并在本机 JSON 状态文件中保存签到记录，未将签到记录写回学校后端。如果要求学校系统留存正式考勤，后端需另行提供有鉴权、幂等且审计留痕的签到写入接口，并确认：

- 场次标识、班级标识、学生标识、终端标识、签到时间的字段及主键/幂等规则。
- 后端如何确认当前场次有效、学生属于该班级，以及教师有权操作该班级。
- 对无效身份证、非本班学生、重复签到、请假、场次已结束等情况返回稳定错误码。
- 是否允许客户端提交完整身份证号。优先由后端核验，持久化时只保存必要标识，避免存储原始身份证号。
- 签到记录的查询、更正、保留期限和审计要求。

## 教师端局域网协议（当前实现）

教师端本地服务提供以下接口，学生端使用 `teacherUrl` 访问：

- `GET /health` → `{ "status": "ok" }`
- `GET /api/v1/session` → `{ "session": null | { "id", "classId", "className", "departmentName?", "startedAt", "active" } }`
- `POST /api/v1/checkins`，JSON 请求 `{ "sessionId", "idCard", "stationId" }`。成功返回 HTTP 201 和 `{ "code":"SUCCESS", "message", "studentName", "className", "departmentName?", "signedAt", "stationId" }`；失败返回相应业务码，如 `INVALID_ID_CARD`、`NO_ACTIVE_SESSION`、`NOT_IN_CLASS`、`ALREADY_SIGNED`、`ON_LEAVE`。

该接口目前没有独立的网络身份认证，依赖教师机防火墙、可信 HTTPS 和部署网络隔离。对开放到非本机网卡的部署，必须配置 TLS；不要在不可信网络上开放服务。
